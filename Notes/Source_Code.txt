/*
 * ===================================================================
 * SECTION 8: OPEN SOURCE, REMOTES, AND TAGGING (VERSIONS)
 * ===================================================================
 *
 * 1. THE OPEN SOURCE REALITY (Why you cannot push)
 * -------------------------------------------------------------------
 * When you clone a massive public project (like React or Linux), you 
 * get a 100% complete local copy. You can make branches, edit code, 
 * and commit locally. 
 * 
 * THE CATCH: If you try to run 'git push', GitHub will block you. 
 * You do not have "Write Access" to their server. Only official 
 * contributors can push directly. (If you want to suggest a change to 
 * their code, you have to use a workflow called "Forking and Pull Requests").
 *
 * 2. CHECKING YOUR CONNECTIONS (git remote -v)
 * -------------------------------------------------------------------
 * SCENARIO: You cloned a project, or you just set up SSH, and you want 
 * to verify exactly which server URL your local Git is trying to talk to.
 * 
 * COMMAND: git remote -v
 * - The '-v' stands for "verbose" (meaning "give me more details").
 * - WHAT IT DOES: It lists all remote connections attached to your 
 *   project, showing both the URL used for fetching (downloading) 
 *   and pushing (uploading).
 * - Example Output:
 *   origin  git@github.com:facebook/react.git (fetch)
 *   origin  git@github.com:facebook/react.git (push)
 *
 * 3. INSPECTING HISTORY & CODE (git show)
 * -------------------------------------------------------------------
 * SCENARIO: You see a specific commit hash in 'git log', or a specific 
 * version tag, and you want to know exactly what code was changed.
 * 
 * COMMAND: git show <commit-hash> OR git show <tag-name>
 * - WHAT IT DOES: It acts like a magnifying glass. It dives into that 
 *   specific snapshot and shows you the author, the date, the commit 
 *   message, and a line-by-line diff (the green additions and red 
 *   deletions) of exactly what was altered in that version.
 *
 * 4. MANAGING VERSIONS (git tag)
 * -------------------------------------------------------------------
 * SCENARIO: Your project has hundreds of commits. You want to mark 
 * one specific commit as "Version 1.0" so people can easily download 
 * the stable release instead of digging through random commit hashes.
 *
 * WHAT IS A TAG?
 * A tag is just a permanent sticky note attached to a specific commit. 
 * Unlike branches (which move forward when you add code), tags NEVER 
 * move. They are frozen snapshots in time.
 *
 * HOW TO SET UP AND USE TAGS:
 * 
 * Step 1: List existing tags
 * Command: git tag
 * (Shows you all versions currently in the project, e.g., v1.0, v2.1.3).
 *
 * Step 2: Create a lightweight tag
 * Command: git tag v1.0
 * (This attaches a "v1.0" sticky note to your MOST RECENT commit).
 *
 * Step 3: Create an annotated tag (Industry Standard)
 * Command: git tag -a v1.0 -m "Initial Stable Release"
 * (This creates a richer tag that includes the date, who created it, 
 * and a message, exactly like a commit).
 *
 * Step 4: Pushing tags to GitHub
 * THE CATCH: Running a normal 'git push' DOES NOT upload tags! 
 * Git assumes tags are strictly local unless you tell it otherwise.
 * Command: git push origin v1.0 
 * (Or use 'git push origin --tags' to upload every local tag at once).
 */
