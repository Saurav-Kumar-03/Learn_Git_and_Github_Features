/*
 * ===================================================================
 * SECTION 7: THE GITHUB CONNECTION (A DEEP DIVE)
 * ===================================================================
 *
 * PHASE 1: CREATING THE REPOSITORY ON GITHUB
 * -------------------------------------------------------------------
 * Before your terminal can talk to GitHub, GitHub needs to prepare a
 * receiving dock.
 * 1. You log into GitHub.com and click "New Repository".
 * 2. You give it a name (e.g., Learn_Git_and_Github_Features).
 * 3. GitHub creates an empty vault on their servers and gives you a
 *    unique URL pointing to that specific vault.
 *
 * PHASE 2: THE AUTHENTICATION DILEMMA (HTTPS vs. SSH)
 * -------------------------------------------------------------------
 * Now you need to send your local code to that URL. But GitHub won't
 * just let anyone upload code to your vault. You have to prove who you
 * are. You have two ways to build this bridge:
 *
 * Option A: HTTPS (The Old/Beginner Way)
 * - The URL looks like: https://github.com/Saurav/project.git
 * - How it works: Every time you try to upload code, the terminal stops
 *   and asks for your GitHub username and a "Personal Access Token"
 *   (a long, ugly password generated on GitHub's website).
 * - The flaw: It is tedious, and typing passwords in terminals is
 *   annoying and prone to typos.
 *
 * Option B: SSH (The Professional Standard - What you used)
 * - The URL looks like: git@github.com:Saurav/project.git
 * - What it is: SSH stands for "Secure Shell". It is a cryptographic
 *   network protocol for operating network services securely.
 * - How it works: Instead of a password, you use 'ssh-keygen' to create
 *   two puzzle pieces:
 *   1. The Private Key (id_ed25519): Stays securely on your hard drive.
 *   2. The Public Key (id_ed25519.pub): You upload this to GitHub.
 * - The Magic: When you push code, GitHub sees the incoming connection,
 *   checks if the computer sending the code holds the matching Private Key,
 *   and if they fit together perfectly, it lets the code through instantly
 *   without ever asking for a password.
 *
 * PHASE 3: DEFINING THE CONNECTION (git remote)
 * -------------------------------------------------------------------
 * Command: git remote add origin <URL>
 *
 * Let's break down every single word:
 * - 'git' : Wake up the Git software.
 * - 'remote' : We are about to configure a connection to a server
 *   on the internet (not a local file).
 * - 'add' : Create a new connection profile.
 * - 'origin' : THIS IS JUST A VARIABLE NAME! You could legally type
 *   'git remote add banana <URL>', and it would work perfectly. But
 *   by industry standard, developers universally name their primary
 *   central server "origin" (because it is the origin point for the
 *   team's code).
 * - '<URL>' : The exact address of your GitHub vault.
 *
 * Summary: You are telling Git, "Save this long SSH URL as a shortcut
 * variable named 'origin'."
 *
 * PHASE 4: UPLOADING THE CODE (git push)
 * -------------------------------------------------------------------
 * Command: git push -u origin main
 *
 * Let's break down every single word:
 * - 'git push' : Take all my local commits and upload them to the internet.
 * - 'origin' : Send them to the URL we saved in the shortcut named 'origin'.
 * - 'main' : Send my local branch named 'main' to GitHub's 'main' branch.
 *
 * What is the '-u'?
 * - '-u' stands for 'upstream'.
 * - When you do this for the very first time, Git doesn't know that
 *   your local 'main' branch is supposed to be permanently linked to
 *   GitHub's 'main' branch.
 * - By using '-u', you are creating a permanent tracking link.
 * - The Result: Tomorrow, when you make a new commit, you don't have to
 *   type 'git push origin main' anymore. You just type 'git push', and
 *   Git remembers the '-u' link you created today.
 */
